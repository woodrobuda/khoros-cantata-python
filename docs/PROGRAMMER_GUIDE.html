Khoros/Cantata Python — Programmer Guide

This guide explains the code in plain language. The main idea is to preserve the old system's meaning while replacing its old executable machinery with Python.

2. How a workspace is executed

  1. HistoricalWorkspaceParser reads the text file.
  2. It creates HistoricalGlyph and HistoricalConnection objects.
  3. WorkspaceExecutor.restore() creates Python graph nodes.
  4. Each node looks up its operator in NativeOperatorRegistry.
  5. When the graph runs, data is published through output ports.
  6. Connections deliver that data to input ports.
Why this matters: the old command line is kept as historical information, but it is not treated as Python code and is not passed to a shell.

3. Why the code is split into layers

The project uses layers because the original Khoros system used layers. A graph should not need to know how a VIFF file is stored. A VIFF reader should not need to know how a Cantata window looks. Keeping the layers separate makes testing easier.

4. Adding a native operator

from khoros_cantata.workspace_runtime import NativeOperatorRegistry

registry = NativeOperatorRegistry()

def add(params, inputs):
    return {"o": inputs["a"] + inputs["b"]}

registry.register("DATAMANIP", "myadd", add)

The function receives two dictionaries. params contains settings from the operator command. inputs contains data from input ports. It returns a dictionary keyed by output-port name.

5. Reading a VIFF file

from khoros_cantata.viff import read_viff

obj = read_viff("sample.viff")
for name, segment in obj.segments.items():
    print(name, segment.data.shape, segment.data.dtype)

Do not throw away the segment metadata. Khoros used more than one kind of data segment, including value, location, time, mask, and map information.

6. Testing

Run the release tests with:

pytest -q tests

The release tests include the Phase 21 numerical checks, workspace parsing, and the KForms parser. The historical Khoros executable is not required.

7. Evidence levels

The final operator matrix has three important evidence levels:

  • Behaviorally validated: direct comparison or strong historical test evidence was available.
  • Source-contract closed: the recovered source gives a clear contract, but the old executable oracle was unavailable.
  • Native baseline: a Python implementation surface exists, but behavioral closure is still open.

Never change a native baseline to “validated” just because its code runs. Validation needs evidence.

8. Legacy-independence rule

Production Python code must not call subprocess, a shell, kexec, or an old Khoros executable. Historical names may appear in documentation because programmers need to understand what was replaced.

9. Extending the project safely

  1. Find the old source behavior first.
  2. Write a small Python function that states the rule clearly.
  3. Add a test using historical data if available.
  4. Record whether the old executable was available for comparison.
  5. Only then mark the operator at the stronger evidence level.
